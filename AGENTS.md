# OneDoor

Human-owned file. Agents: do not edit this file. Propose changes to the human instead.

OneDoor is a self-hosted MCP gateway. An admin installs upstream MCP servers in a web UI.
Agents then connect to one MCP endpoint that exposes exactly two tools, `search` and
`execute`, over the whole catalog of installed tools. Finding the right tool, quickly, is
the product. This is a proof of concept that currently runs only on the developer's machine.

## Layout

```
/AGENTS.md            this file
/server               NestJS backend (own package.json, lockfile, tsconfig, Dockerfile)
/web                  TanStack Start frontend (own package.json, lockfile, tsconfig, Dockerfile)
/specs                one Markdown spec per capability (human-owned)
/scenarios            acceptance scenarios and the search golden set (human-owned)
/tasks/TODO.md        task list, one small vertical slice per item
/docker-compose.yml   Postgres (pgvector), Redis, api, web, proxy, optional trace viewer
```

This is NOT a monorepo. No workspaces, no shared packages. A root `package.json`, if
present, holds dev tooling only (Biome, git hooks).

Read `server/AGENTS.md` or `web/AGENTS.md` before working in that folder.

## Hard rules

1. **No imports between `server` and `web`**, in either direction, by any path.
   The only contract is `server/schema.gql` (generated by the server, committed).
   `web` reads it as a file for codegen. That is a file read, not an import.
2. **Replaceable parts sit behind an interface.** Search, embeddings, LLM access, secret
   storage, the event bus and upstream auth each have an abstract class and are chosen by
   config. Do not call a vendor SDK from feature code. See `server/AGENTS.md`.
3. **Secrets never leave the server.** Never log them, never return them from GraphQL,
   never put them in the web bundle, never commit them. `.env` files are not committed;
   `.env.example` is.
4. **Do not weaken the checks.** No `.skip`, `.only`, `biome-ignore`, `@ts-ignore`,
   `@ts-expect-error` without a linked reason, or `as any`. Do not delete or loosen tests
   to make them pass. If a check seems wrong, stop and say so.
5. **Do not edit protected paths:** `AGENTS.md` files, `specs/`, `scenarios/`,
   `server/test/twins/`, `biome.json` files, `tsconfig*.json`, test runner configs,
   git hook config, and `verify` scripts. Ask the human.
6. **Check current docs before using these libraries.** They are newer than most model
   training data and their APIs changed recently: NestJS 12, `@nestjs/mcp`, the MCP
   TypeScript SDK v2 (`@modelcontextprotocol/server` and `/client`), Prisma 7,
   TanStack Start, TanStack AI, Apollo Client 4, Biome 2. Do not write their APIs from
   memory. Use the Context7 MCP server to fetch the current documentation for a library
   before you write code against it. For NestJS, `https://docs.nestjs.com/llms.txt`
   indexes every chapter.

## Skills

Agent skills are installed in `.claude/skills/` and `.agents/skills/`: the official
NestJS skills, Matt Pocock's engineering skills, Prisma's skills, a community set of
TanStack skills, and shadcn.

**Where a skill and an `AGENTS.md` file disagree, `AGENTS.md` wins.** The NestJS
differences are listed in `server/AGENTS.md`. Skills can be out of date; current docs
from Context7 win over a skill's API details.

Do not use these installed skills in this project:

- `tanstack-query`, `tanstack-db`: data fetching here is Apollo Client with GraphQL.
- `setup-pre-commit`: it sets up Husky and Prettier. This project uses Biome.
- `prisma-compute`, `prisma-postgres`, `prisma-postgres-setup`: hosted Prisma products.
  The database is PostgreSQL in Docker.
- `migrate-radix-to-base`: not relevant.

The Prisma skills may describe Prisma 8. This project is pinned to Prisma 7; check the
version a skill is talking about before following it.

## How work is done

- A feature starts as a spec in `specs/` with requirements and WHEN/THEN scenarios.
  Requirement ids look like `REQ-SEARCH-003`. Put the id in the title of the test that
  covers it.
- Work one task from `tasks/TODO.md` at a time, on its own branch, as a thin vertical slice.
- A task is done when `pnpm verify` passes in every project it touched. Run it yourself
  before saying the task is finished, and report the actual result.
- If a spec is unclear or contradicts the code, stop and ask. Do not guess the intent.
- Commit small, with a clear message. Do not push. There is no CI yet; the local
  `verify` command is the gate.

## Checkpoints: stop after the first of each pattern

The human wants to approve naming, file locations and setup before a pattern is repeated.
Do not build several layers or features in one go.

- Build **one** new kind of thing, then stop and wait for review. A "kind of thing" is
  the first instance of a pattern, for example: the project scaffold, the config setup,
  the first Nest module, the first Prisma model and migration, the first GraphQL model,
  input and resolver, the first interface with its implementation and provider binding,
  the first test of each type, the first route or screen in `web`, the first hook
  wrapper, the Docker Compose file.
- When you stop, show: the files you created as a tree, the names you chose, where
  things live and why, and anything you were unsure about. Keep it short. Then wait.
- Do not start the next pattern, and do not copy this pattern to other features, until
  the human approves or corrects it.
- After approval, record the pattern in `docs/conventions.md` (a short example and the
  rule) and follow it exactly from then on. If a later task does not fit an approved
  pattern, stop and ask instead of inventing a variation.
- Unattended runs are only for work that repeats patterns already in
  `docs/conventions.md`.

## Code the human always reviews

Flag any change to these in your summary, even when all checks pass:

- credential and token storage, encryption, key handling
- the guard on the MCP endpoint and any auth or permission check
- OAuth flows to upstream servers (callbacks, token refresh)
- Prisma migrations
- anything that fetches a URL supplied by an upstream server (icons, OAuth discovery)

## Toolchain

- Node 26, pnpm. One lockfile per project.
- TypeScript, strict. Use the TypeScript major that NestJS 12 supports; check before upgrading.
- Biome 2 for lint and format. Root `biome.json`, with `server/biome.json` and
  `web/biome.json` extending it via `"extends": "//"`.
- Pin exactly: `prisma`, `@prisma/client` and `@prisma/adapter-pg` on major 7 (the npm
  `latest` tag may point at a version 8 pre-release), and `@nestjs/mcp` (it is 0.0.x).

## Current scope

- Upstream servers: remote HTTP only. No locally spawned (stdio) servers yet.
- First servers to support: GitHub, Context7, Azure DevOps.
- Upstream auth: none, token or header, OAuth (automatic), OAuth (manual client details).
- The MCP endpoint has no caller auth yet. A guard and a default caller identity exist so
  auth can be added without changing the tools. Bind to localhost.
- Models (LLM and embeddings) come from OpenRouter for now, behind interfaces, so another
  provider such as Azure can replace it by config.
- Search must work for queries in several languages, not only English.
- Usage analytics tables are deferred. Use normal structured server logging.
