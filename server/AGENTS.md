# OneDoor server

Human-owned file. Agents: do not edit this file. Propose changes to the human instead.
Read `/AGENTS.md` first. Its hard rules apply here.

## Stack

- NestJS 12, ESM project, Node 26, pnpm
- `@nestjs/mcp` for the MCP endpoint; `@modelcontextprotocol/client` (SDK v2) for upstream servers
- Prisma 7 with `@prisma/adapter-pg`, PostgreSQL with the `pgvector` and `pg_trgm` extensions
- GraphQL, code-first, Apollo driver, subscriptions over `graphql-ws`
- Redis: event bus for subscriptions, query-embedding cache, BullMQ job queue
- `@nestjs/config` with a Zod schema; one namespace per area (`registerAs`)
- OpenTelemetry for traces; structured logs to stdout
- Vitest for tests

## Skills: where this project differs

The official NestJS skills are installed. Follow them, except where this list says otherwise:

- **pnpm, not npm.** Scaffold with `--package-manager pnpm` and use `pnpm` in every command.
- **No NestJS Observe.** Scaffold with `--no-observe`. Do not install, configure or link
  `@nestjs/observe`, do not add its MCP server, and do not ask the human to link it.
  Tracing is OpenTelemetry.
- **Persistence is Prisma 7.** Ignore the Drizzle and TypeORM instructions in
  `nestjs-data`. Its general rules (scope by owner in the query, map constraint
  violations, short transactions, one Prisma client) still apply.
- **The admin API is GraphQL.** The HTTP controller guidance in `nestjs-feature` applies
  only to the few plain HTTP routes (health checks, the OAuth callback, icons).
- **No `@nestjs/authentication` or `@nestjs/authorization` yet.** Do not add them until a
  spec asks for caller auth.
- **`nest new` generates its own `AGENTS.md`.** Do not let it overwrite this file. If it
  contains useful commands, report them to the human.

## Interfaces

Write each as an **abstract class** (it doubles as the Nest injection token). Bind the
implementation with a factory provider that reads config. Feature code depends on the
abstract class only.

| Abstract class | Job | First implementation |
|---|---|---|
| `Retriever` | one search arm: `upsert`, `deleteByServer`, `search(query, filter, limit)` | `PgFtsRetriever`, `PgVectorRetriever` |
| `Fuser` | merge ranked lists | reciprocal rank fusion, `k = 60`, set explicitly |
| `Embedder` | `embedQuery`, `embedDocuments`; exposes `id` and `dimensions` | OpenRouter, multilingual model |
| `ToolDocumentBuilder` | build the indexed text for a tool; exposes `version` | template v1 |
| `ExampleQueryGenerator` | write example queries for a tool | via `LlmClient` |
| `Reranker` | optional final rerank | pass-through |
| `LlmClient` | generate an object matching a schema | OpenRouter |
| `SecretStore` | encrypt and decrypt secrets | AES-256-GCM, key from config |
| `EventBus` | publish and subscribe across instances | Redis |
| `UpstreamAuthProvider` | supply credentials for an upstream connection | none, token, OAuth |

Rules:

- `SearchFilter` (the caller and optional connection ids) is a required argument of every
  `Retriever.search`. Permission filtering happens inside each retriever, never after.
- Every implementation has an `id` or `version`. Log which ones answered each search.
- Code asks `LlmClient` and `Embedder` for a **role** (for example `example-generation`),
  never a model name. Config maps roles to models.
- The server must run as several instances. Keep no per-instance state that another
  instance needs; Postgres is the source of truth, Redis carries events and cache.

## MCP endpoint

- Exactly two tools: `search` and `execute`. Do not add tools without a spec.
- `search` takes an array of full-sentence queries and an optional server filter. It
  returns about five tools per query, each with its id, description and input schema, so
  the caller can go straight to `execute`.
- `execute` takes a tool id and an arguments object. Look the tool up by id in the
  database; never parse the id string. Check the tool policy, validate the arguments
  against the stored JSON Schema, forward to the upstream client, and return the upstream
  result unchanged.
- `execute` declares no `outputSchema`, so upstream results pass through.
- Failures the model can act on (unknown tool, invalid arguments, policy denied, upstream
  error) are **returned** as a result with `isError: true` and a useful message. Do not
  throw them. Do not retry a call automatically after a dropped connection.
- A guard is attached to the endpoint. Today it allows every request and attaches the
  seeded user `me` as the caller. Tools read the caller from the request context, never
  assume "no auth".
- Tool providers and everything they call are default-scoped (no request scope).

## Search

- One enriched document per tool: server name and description, tool name split into
  words, description, flattened parameters (name, type, description), and generated
  example queries. Never embed raw JSON Schema.
- Split tool names in TypeScript before indexing and before querying: on `_`, `-`, `.`,
  `/` and camelCase boundaries. Keep the whole identifier as an extra token.
- Vectors: exact scan with pgvector. No HNSW or other approximate index. Normalised
  float32 at the model's native dimension.
- Vectors live in a side table `tool_embedding` keyed by `(tool_id, model_id)`, with the
  template version and a hash of the embedded text. Re-embed only when the hash changes.
- The vector column is `Unsupported(...)` in the Prisma schema. Raw SQL (`$queryRaw`,
  `$executeRaw`) is allowed **only inside `Retriever` implementations**. Cast counts to
  `int` and scores to `float8` in raw queries.
- Cache query embeddings in Redis, keyed by model id and text. If the embedding call
  fails or is slow, return keyword-only results instead of failing the search.
- An exact or near-exact tool-name match ranks first.

## Upstream connections

- One singleton registry owns all upstream MCP clients. Connect in
  `onApplicationBootstrap` without blocking startup. Close clients in `onModuleDestroy`;
  shutdown hooks are enabled.
- Remote HTTP servers only for now.
- On install or tool-list change: queue a job that diffs tools by content hash, generates
  example queries, embeds, and updates the index. A tool with a pending embedding stays
  findable by keyword.
- Tool policy: the owner enables or disables each tool, and a new tool is enabled. There
  is no connection mode and no tool class. MCP tool annotations (read-only, destructive)
  are untrusted hints: show them as labels, never enforce them. `search` hides disabled
  tools and `execute` rejects them. The `execute` check is the one that counts.
- Server icons: see REQ-CONN-070 and REQ-CONN-071 in `specs/connections.md`.

## Secrets

- Encrypt every token, header value, client secret and refresh token with `SecretStore`
  before it reaches Prisma. Store a key id with each value.
- GraphQL inputs accept secrets. No GraphQL field, log line or error message returns one.
  Expose only whether a secret is set.

## GraphQL

- Code-first. File names per feature: `x.model.ts` (`@ObjectType`), `x.input.ts`
  (`@InputType`), `x.args.ts` (`@ArgsType`), `x.resolver.ts`.
- Validate inputs with `class-validator` decorators on the input class.
- GraphQL models are separate classes from Prisma models. Never return a Prisma type directly.
- The schema is emitted to `server/schema.gql` and committed. If your change alters it,
  commit the new file; `verify` fails when the emitted schema differs from the committed one.
- Subscriptions publish through `EventBus`. Send ids in events and load the row in the resolver.
- GraphQL serves the web UI only. Agents use `/mcp`.

## Errors

- Services throw a small set of domain errors (not found, conflict, forbidden, validation,
  upstream unavailable). Nothing outside the data layer sees a Prisma error.
- One mapper translates known Prisma error codes to domain errors. Unknown errors become
  an internal error with the message hidden from clients.
- One global filter, registered with `APP_FILTER`, turns domain errors into GraphQL errors
  with a stable `extensions.code`, or into HTTP status codes.
- MCP tool errors follow the MCP endpoint rules above, not the filter.

## Prisma

- Stay on Prisma 7. Use the `prisma-client` generator with an explicit `output`, and the
  `PrismaPg` driver adapter.
- Extensions, the vector column and the full-text column and index are added by editing
  the migration SQL created with `--create-only`.
- Migrations are human-reviewed. Create them, do not apply destructive ones without asking.

## Logging

- Structured logs to stdout. Redact tokens and auth headers.
- Log one line per search (queries, returned tool ids with ranks, which implementations
  answered, duration) and one per execute (tool id, duration, outcome). Do not log tool
  arguments or results.

## Tests

- Vitest. Test the MCP tools through `connectMcpClient` from `@nestjs/mcp/testing`.
- Database tests run against a real Postgres with pgvector, started by Testcontainers.
- Fake upstream MCP servers live in `test/twins/` and are human-owned.
- Tests never call OpenRouter or any external network. Override `Embedder` and `LlmClient`
  with deterministic fakes.
